# Domain Model

**Version:** 1.0
**Status:** Draft / Architecture Proposal
**Project:** FinCore Platform

---

# 1. Purpose

This document defines the main business entities and concepts of the FinCore platform.

The purpose is to establish a shared understanding of:

* what each business entity represents;
* which Business Domain owns it;
* what responsibilities it has;
* what it does not own;
* how it is created and changed;
* how it relates to other entities;
* which entities may become Aggregate Roots;
* which concepts may become Value Objects;
* how the model can evolve without creating tight coupling.

This document describes the **business domain model**.

It does not define:

* Angular classes;
* TypeScript interfaces;
* database tables;
* Firebase collections;
* REST DTOs;
* UI components.

Those concerns belong to later architectural layers.

---

# 2. Domain Modeling Principles

FinCore follows the following principles.

## 2.1 Business Ownership

Every important business entity must have a clear owner.

```text
Entity
   ↓
Business Domain
```

An entity should not be owned by multiple domains.

---

## 2.2 No Shared Domain Entities

We should not create a global domain model such as:

```text
shared/
    User
    Company
    Bank
    Account
```

and make every domain use those classes.

This creates tight coupling.

Instead, each Bounded Context owns the model it needs.

For example:

```text
Banking
    Customer

Compliance
    Customer Risk Profile

Fraud
    Customer Risk

Analytics
    Customer Analytics View
```

The same real-world person may appear in multiple contexts, but each context has its own model.

---

# 3. Entity Categories

The domain model contains several types of concepts.

## Entity

An object with a unique identity and lifecycle.

Examples:

```text
Account
Company
Bank
Card
Loan
Payment
```

---

## Aggregate Root

An entity that controls consistency boundaries inside an Aggregate.

Examples that may become Aggregate Roots:

```text
Workspace
Company
Bank
Bank Account
Card
Payment
Loan
Subscription
```

The final Aggregate boundaries will be defined later.

---

## Value Object

An object defined by its value rather than identity.

Examples:

```text
Money
Currency
Address
Email
Phone Number
Date Range
Tax Number
Percentage
Risk Score
```

---

## Domain Event

A fact that something important happened.

Examples:

```text
AccountRegistered
CompanyCreated
BankCreated
PaymentCompleted
LoanApproved
KYCCompleted
```

---

# 4. Identity & Access Domain

---

# 4.1 Account

## Purpose

Represents the digital identity of a person inside FinCore.

Account is **not a bank account**.

It represents the person who can authenticate into the platform.

---

## Business Owner

```text
Identity & Access
```

---

## Responsibilities

Account is responsible for:

* identity;
* authentication state;
* credentials;
* security configuration;
* account status;
* authentication methods.

Potential information:

```text
Account Id
Email
Phone
Status
Authentication Methods
Created At
Updated At
```

---

## Does NOT Own

Account does not own:

* Company;
* Bank;
* Workspace;
* Membership;
* Bank Account;
* Card;
* Payment;
* Loan;
* Deposit;
* Employee information.

---

## Lifecycle

```text
Register
    ↓
Account Created
    ↓
Account Active
    ↓
Account Suspended
    ↓
Account Deactivated
```

Account should normally be deactivated rather than physically deleted.

---

## Relationships

```text
Account
   │
   ├── Membership *
   │
   ├── Session *
   │
   └── Authentication Method *
```

---

# 4.2 Session

## Purpose

Represents an authenticated session of an Account.

## Owner

```text
Identity & Access
```

## Responsibilities

* session lifecycle;
* authentication state;
* expiration;
* device/session information;
* session revocation.

## Does NOT Own

Session does not own:

* permissions;
* business roles;
* bank accounts;
* company membership.

---

# 4.3 Authentication Method

Represents a way in which an Account authenticates.

Examples:

```text
Password
Google
Microsoft
Apple
Passkey
MFA
```

The domain should support multiple authentication methods for one Account.

---

# 5. Organization Management Domain

---

# 5.1 Workspace

## Purpose

Workspace represents the operational environment in which a user works.

This is one of the most important entities in the platform.

The user does not simply enter "the application".

The user enters a Workspace.

---

## Business Owner

```text
Organization Management
```

---

## Responsibilities

Workspace is responsible for:

* workspace identity;
* workspace type;
* workspace status;
* enabled products;
* workspace configuration;
* participants;
* business context.

---

## Workspace Types

Possible types:

```text
Personal
Company
Bank
Platform
```

Future types may be added.

---

## Example

```text
Maxim

Workspace Selection

├── My Factory Ltd
├── Business Bank
└── Personal Banking
```

The same Account can participate in all three.

---

## Does NOT Own

Workspace does not directly own:

* authentication;
* passwords;
* banking accounts;
* transactions;
* payment execution.

It provides the business context in which those operations happen.

---

## Lifecycle

```text
Workspace Created
        ↓
Workspace Configured
        ↓
Workspace Activated
        ↓
Workspace Suspended
        ↓
Workspace Archived
```

---

# 5.2 Membership

## Purpose

Membership represents the relationship between an Account and a Workspace.

This is one of the most important concepts in FinCore.

The system should not store relationships such as:

```text
Account.companyId
Account.bankId
Account.role
```

Instead:

```text
Account
    ↓
Membership
    ↓
Workspace
```

---

## Business Owner

```text
Organization Management
```

---

## Responsibilities

Membership controls:

* membership relationship;
* role;
* permissions;
* status;
* access period;
* invitation information;
* membership lifecycle.

---

## Example

```text
Account: Maxim

Membership
    Workspace: My Factory Ltd
    Role: Owner

Membership
    Workspace: Business Bank
    Role: Bank Manager

Membership
    Workspace: Personal Banking
    Role: Customer
```

---

## Does NOT Own

Membership does not own:

* Account credentials;
* Company;
* Bank;
* Card;
* Payment;
* financial data.

It owns only the relationship.

---

## Lifecycle

```text
Invitation Sent
      ↓
Invitation Accepted
      ↓
Membership Created
      ↓
Membership Active
      ↓
Membership Suspended
      ↓
Membership Revoked
```

Historical Membership records should normally be retained.

---

# 5.3 Company

## Purpose

Represents a legal/business organization using FinCore.

---

## Owner

```text
Organization Management
```

---

## Responsibilities

* company identity;
* company information;
* organization structure;
* employees;
* business configuration;
* company lifecycle.

---

## Relationships

```text
Company
   │
   ├── Workspace
   │
   ├── Membership *
   │
   ├── Department *
   │
   └── Employee *
```

---

## Does NOT Own

Company does not directly own:

* authentication;
* user passwords;
* bank infrastructure;
* payment execution logic.

---

# 5.4 Employee

## Purpose

Represents a person working for a Company.

Employee is a business relationship, not an identity.

A person may have:

```text
Account
```

and separately:

```text
Employee
```

inside a company.

---

## Owner

```text
Organization Management
```

---

## Responsibilities

* employment relationship;
* employment status;
* department;
* position;
* payroll relationship;
* employee metadata.

---

## Important Distinction

```text
Account
    = Who is the person?

Employee
    = What is the person's relationship with this company?
```

---

# 5.5 Department

Represents an organizational unit inside a Company.

Examples:

```text
Engineering
Accounting
HR
Sales
Management
```

---

# 5.6 Invitation

Represents an invitation to join a Workspace.

Responsibilities:

* invited Account/email;
* target Workspace;
* intended role;
* invitation status;
* expiration;
* inviter.

# 6. Banking Domain

---

# 6.1 Bank

## Purpose

Represents a bank operating on the FinCore platform.

This is a key business entity.

---

## Owner

```text
Banking
```

---

## Responsibilities

* bank identity;
* bank configuration;
* banking products;
* customers;
* account services;
* card services;
* loan services;
* deposit services;
* bank lifecycle.

---

## Important Concept

Two banks can use the same FinCore platform while providing completely different:

* branding;
* products;
* fees;
* limits;
* workflows;
* approval processes;
* customer experiences.

---

## Example

```text
FinCore Platform

├── Bank A
│   ├── Premium Cards
│   ├── Business Loans
│   └── High-Yield Deposits
│
└── Bank B
    ├── Basic Cards
    ├── FOP Services
    └── Payroll
```

---

# 6.2 Customer

## Purpose

Represents a person or organization receiving services from a Bank.

Customer is a banking concept.

It is not the same thing as Account.

---

## Owner

```text
Banking
```

---

## Important Distinction

```text
Account
    = Platform identity

Customer
    = Relationship with a Bank
```

One Account may become a Customer of multiple Banks.

---

## Example

```text
Account
   │
   ├── Customer → Bank A
   │
   ├── Customer → Bank B
   │
   └── Customer → Bank C
```

---

# 6.3 Bank Account

## Purpose

---

## Owner

```text
Banking
```

---

## Responsibilities

## Important Distinction

## Owner

## Responsibilities

* card status;

---

## Lifecycle

# 6.5 Deposit

Represents a deposit product opened by a customer.

Responsibilities:

* principal;
* interest rate;
* term;

---

Responsibilities:

# 7. Financial Operations Domain

---

# 7.1 Payment

## Purpose

Represents an instruction to move money.

---

## Owner

```text
Financial Operations
```

---

## Responsibilities

* source;
* destination;
* amount;
* currency;
* payment status;
* execution lifecycle;
* payment metadata.

---

## Lifecycle

```text
Payment Created
      ↓
Payment Validated
      ↓
Compliance Checked
      ↓
Fraud Checked
      ↓
Payment Approved
      ↓
Payment Executed
      ↓
Payment Completed
```

---

## Does NOT Own

Payment does not own:

* Bank Account;
* Customer;
* Fraud rules;
* KYC rules.

It references those contexts through contracts.

---

# 7.2 Money

Money should be represented as a Value Object.

Example:

```text
Money
    amount
    currency
```

It should not be represented as:

```text
number balance
```

because currency is part of the business meaning.

---

# 7.3 Transaction

Represents a recorded financial movement.

A Transaction is different from a Payment.

```text
Payment
    = intention / instruction

Transaction
    = recorded financial movement
```

This distinction will become important later.

# 24. Critical Entity Distinctions

These distinctions are mandatory.

## Account vs Bank Account

```text
Account
    = Platform identity

Bank Account
    = Financial account
```

---

## Account vs Customer

```text
Account
    = Person's platform identity

Customer
    = Person/organization's relationship with a Bank
```

---

## Account vs Employee

```text
Account
    = Person

Employee
    = Employment relationship
```

---

## Company vs Workspace

```text
Company
    = Business/legal organization

Workspace
    = Operational environment in FinCore
```

A Workspace may represent a Company, but they are not conceptually identical.

---

## Payment vs Transaction

```text
Payment
    = Instruction to move money

Transaction
    = Recorded financial movement
```

---

## Marketplace Product vs License

```text
Marketplace Product
    = Something that can be purchased

License
    = Authorization to use it
```

---

## Theme vs Brand Configuration

```text
Theme
    = Commercial visual product

Brand Configuration
    = Active configuration applied to a Workspace
```

---

## Fraud Risk vs Compliance Risk

```text
Fraud Risk
    = Suspicious behavior / transaction risk

Compliance Risk
    = Regulatory / customer verification risk
```

# 28. Model Evolution Rules

The domain model must evolve according to the following rules.

## Rule 1

Do not create an entity only because a database table is required.

---

## Rule 2

Do not create a shared domain entity simply to avoid duplication.

---

## Rule 3

A domain owns its business invariants.

---

## Rule 4

An entity should have a clear business responsibility.

---

## Rule 5

If two contexts use the same real-world concept, they may have different domain representations.

---

## Rule 6

New business functionality should first be mapped to an existing Capability.

If no Capability owns it, consider creating a new Capability.

If no existing Bounded Context owns that Capability, consider creating a new Context.

---

# 29. Extensibility Example

Suppose the platform later introduces Insurance.

We should not modify:

```text
Banking
Customer
Loan
Payment
```

Instead:

```text
Insurance Context

Policy
Coverage
Premium
Claim
Insurance Customer
```

The new context communicates with existing contexts through explicit contracts.

# 30. Final Domain Model Direction

The target architecture is:

```text
Platform
    │
    ├── Products
    │
    ├── Business Domains
    │
    └── Bounded Contexts
             │
             ├── Aggregates
             │
             ├── Entities
             │
             ├── Value Objects
             │
             ├── Domain Services
             │
             └── Domain Events
```

The domain model is intentionally independent from:

```text
Angular
Nx
Firebase
REST
HTTP
UI
Database
```

Those are implementation concerns.

```text
docs/02-architecture/ddd/bounded-contexts.md
```

with the entities and events defined here.

It will answer:

* which context owns which data;
* which context depends on which;
* which relationships are upstream/downstream;
* where Domain Events are required;
* where synchronous communication is acceptable;
* where eventual consistency is preferable;
* where Anti-Corruption Layers are required;
* where integration contracts should exist.

After Context Map, we will move to:

```text
Aggregates
    ↓
Aggregate Invariants
    ↓
Domain Services
    ↓
Domain Events
    ↓
Application Services
```

Only after these steps should the domain model be translated into the actual Angular/Nx monorepo architecture.
